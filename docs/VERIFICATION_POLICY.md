# Verification Policy and Evidence Semantics

## Statuses

`VERIFIED` — live public retrieval, structural checks and constrained semantic review all passed; all candidate claims have independently fetched verbatim supporting quotes, each verified with a different source family than the extraction claim, and no omitted prerequisite was reported.

`NEEDS_REVIEW` — any structural, evidence, missing-prerequisite or semantic check failed. A candidate may still contain useful facts, but it is blocked from investigation.

`DEMO_ONLY` — a local educational fixture passed its mocked checks. This is **not** real-world CVE verification and requires explicit `--allow-demo` to run against provided local examples.

## Verification gate — actual code behavior

The check engine requires:

1. Official published CVE/CNA source record.
2. At least two separately retrieved source families.
3. At least one condition and nonempty applicability logic.
4. All condition IDs unique, and every condition used in the logic.
5. Every candidate quote is a literal contiguous substring of the cited source text after whitespace normalization.
6. A verifier decision for every candidate condition.
7. All decisions labeled `SUPPORTED`; no unsupported or contradictory conditions.
8. Verifier's support cited with a literal quote from a different source family.
9. No missing prerequisites with valid evidence.
10. Declarative probe types and the WordPress plugin directory are checked for consistency.

If any check fails, the Skill remains `NEEDS_REVIEW`. The extraction model receives structured issues and may repair the candidate up to three times. Missing source families are not fixed by stochastic retries and stop the loop early.

**Caveat:** different retrieved publishers can reproduce the same CNA claim; cross-source support here does not prove independent security research. The policy explicitly favors refusing uncertain Skills rather than inflating the pass rate. Future work should add source-origin graphs and patch-level independent verification.

## What is NOT proof

- JSON Schema validity alone.
- A model returning `SUPPORTED` without a matching source quote.
- A vendor claim repeated on a secondary website.
- A successful automatic repair loop, absent source evidence.
- An affected software version without required configuration.
- A guessed WordPress option key (not accepted as automatically observed configuration).
- An unreachable endpoint without validated reachability measurement.
- The absence of a matching suspicious log line.

## Why source quotes matter

Each generated condition stores its source ID and verbatim evidence text. The verifier independently looks for the same fact in newly fetched evidence, also using exact quotes. This prevents a model from supplying an invented URL and counting it as corroboration. It does **not** prevent the model from misinterpreting a real quotation, which is why human review remains important.

## What the investigator can conclude

- `NOT_APPLICABLE`: at least one required AND group is definitively false (with this source model and the provided observations).
- `APPLICABLE`: all required groups true, but external exposure has not been established by an explicit exposure predicate.
- `EXPOSED`: the model contains an evidenced exposure predicate that is true alongside all other required conditions.
- `INCONCLUSIVE`: one or more needed facts remain unknown or a probe errored, with no group conclusively false.

The engine does **not** currently emit `EVIDENCE_OF_EXPLOITATION`. It can be added later only with evidence-specific probes and measured error rates. No exploit or external network traffic is generated by `investigate`.

## Trust, integrity and age

`verification.json` includes the SHA-256 hashes of the exact `applicability.json` and `SKILL.md`. The investigator recomputes those hashes. A changed condition or modified instruction invalidates the package. The default maximum acceptable verification age is 30 days and can be adjusted via `--max-age-days`.

**Hashes are not signatures.** Someone who can edit `verification.json` can forge a matching hash; signatures and a trusted issuer registry are outside v0.1. Do not accept untrusted third-party Skill archives as authoritative merely because hashes match.
